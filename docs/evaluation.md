## 실제 업무 문서 평가 준비

2026-10-13: 제공된 PDF 8개(605페이지)·40문항의 첫 실제 예비 평가를 완료했다.
[결과와 후속 교정 범위](#실제-문서-예비-평가-결과--2026-10-1213),
[실행·재개 방법](#실제-문서-예비-평가-실행)을 참고한다. 아래는 새 자료 추가 시의 안내다.

추가 모델 설치 없이 현재 Qwen3-4B와 E5로 평가할 수 있다. 합성 문장 시험으로는
실제 PDF의 OCR 오류·표·문맥 누락과 초안 품질을 확인할 수 없으므로 업무 자료가 필요하다.

### 준비할 자료

1. 대표 PDF 2~3개를 프로젝트의 `data/evaluation-input/`에 두거나 저장 경로를 알려 준다.
   본문 중심 문서와 표/스캔 문서를 하나씩 포함하면 좋다. 평가에 필요 없는 민감 정보는 제외한다.
2. 문서마다 질문 3~5개와 정답이 있는 페이지·원문 문장을 적는다.
3. 답이 없는 질문도 문서마다 1개 넣는다. 이 질문에는 초안이 만들어지면 안 된다.

다음 형식의 텍스트만 있어도 된다. Block ID나 JSON은 직접 작성할 필요 없다.

```text
파일: 운영절차.pdf
질문: 장애가 발생하면 누구에게 연락하나요?
정답 페이지: 3
정답 원문: 장애 발생 시 운영 담당자에게 연락한다.
분류: 문제 해결

파일: 운영절차.pdf
질문: 출장비 지급일은 언제인가요?
정답: 문서에 없음
```

분류는 개요, 사전 조건, 절차, 주의사항, 문제 해결 중 하나다. 여러 문장이 정답이면
각 페이지와 문장을 함께 적는다. 원문에 없는 내용을 정답으로 추가하지 않는다.

### 자료를 받은 뒤 진행할 순서

- PDF 등록과 OCR → 페이지 검토 → 구조·검색 색인 생성
- 사람이 적은 정답과 OCR 원문 연결; OCR 오류와 모델 선택 오류 구분
- 초안 원문 선택·분류·누락·관련 없는 인용, 근거 없음 처리, 생성 시간 측정
- 실제 문서 결과를 합성 시험 보고서와 구분해 기록

평가는 로컬에서 진행한다. PDF를 외부 서비스에 올리거나 Ollama를 추가 설치할 필요는 없다.

## 실제 문서 예비 평가 실행

사용자가 제공한 8개 PDF(605페이지)와 40문항을 대상으로 기존 OCR·Layout·E5·Qwen
발췌 파이프라인을 실행한다. 정답은 `needs_human_review`인 초안이므로 결과도 예비 평가다.
평가 데이터와 PDF는 Git 제외 경로 `data/evaluation-input/`에 보존한다.

첫 전체 실행 결과와 수정 우선순위는 [2026-10-13 결과](#실제-문서-예비-평가-결과--2026-10-1213)에 정리했다.

### 실행과 재개

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_real_documents.py --output data/real-evaluation-20261012 --audit-only
.\.venv\Scripts\python.exe scripts/evaluate_real_documents.py --output data/real-evaluation-20261012
.\.venv\Scripts\python.exe scripts/report_real_evaluation.py --output data/real-evaluation-20261012
```

- `--audit-only`: 전체 PDF 해시·페이지 수·질문 ID·근거 페이지·유답/무답 계약을 검사한다.
- `--prepare-only`: OCR, 기본 구조와 Layout 구조, 전체 문서 검색 색인까지만 실행한다.
- `--documents DOC01 DOC03`: 지정한 문서만 처리한다. 없는 ID는 오류다.
- 동일 출력 폴더로 재실행하면 완료한 OCR·색인·문항 결과를 재사용한다.
- 중단으로 queued/running이 남았으면 **해당 출력 폴더를 쓰는 모든 평가 프로세스가
  종료된 것을 확인한 뒤** `--recover-interrupted`를 한 번 사용한다. 중단 작업을 실패로
  보존하고 재시도한다. 중단 OCR의 일부 페이지만 이어 붙이지 않고 새 처리 버전을 만든다.
- 다른 문서를 `--prepare-only --documents ...`로 나누어 실행할 수 있다. 같은 문서를
  동시에 처리하지 않으며 GPU 초안 생성은 한 프로세스에서 순차 실행한다.
- 정답 파일이나 평가 설정을 변경할 때는 새 출력 폴더를 사용한다.
  모델·프롬프트·코드를 변경한 비교 평가도 새 폴더로 구분한다.

평가 전용 `evaluation.db`, 원본 복사본, 페이지 PNG, Chroma 색인을 출력 폴더에 저장한다.
앱의 `data/handover.db`를 사용하지 않으며 사람 검토 완료 기록을 자동으로 만들지 않는다.
모델은 기존 로컬 경로를 사용하고 다운로드하지 않는다. 기본 한국어 OCR로 영문 문서도
처리하므로 영문 결과는 이 기본 구성에 대한 측정이지 영어 OCR 최적 설정의 성능이 아니다.

### 결과 파일

- `input-audit.json`: 원본 해시·페이지와 PDF 내장 텍스트의 근거 인용문 일치 검사.
  스캔 페이지의 내장 텍스트 부재는 정답 오류를 뜻하지 않는다.
- `DOCxx-ocr.json`: 페이지별 OCR 텍스트.
- `DOCxx-prepared.json`: 등록·OCR·기본 구조·Layout 구조 ID.
- `DOCxx-progress.json`: 완료한 문항별 체크포인트.
- `DOCxx.json`: 문서의 모든 질문을 실행한 결과. 검색 원문과 초안·오류·시간 포함.
- `summary.json`, `summary.md`, `report.html`: 보고서 스크립트로 최신 결과를 집계.
  HTML에서는 문항별 정답 초안·제공 근거·실제 선택 원문을 펼쳐 비교할 수 있다.

### 지표를 읽는 방법

| 지표 | 의미 |
|---|---|
| `ocr_quote_exact` | 정답의 지정 페이지 OCR에 인용문이 공백 제외 완전 일치로 포함되는지 |
| `retrieved_quote_exact` | 상위 5개 검색 Chunk의 원문에 인용문이 포함되는지 |
| `candidate_quote_exact` | 길이·개수·검토 정책 적용 뒤 모델에 전달할 후보에 포함되는지 |
| `selected_quote_exact` | 최종 선택 원문에 인용문이 포함되는지 |
| `all_gold_pages_retrieved` | 정답의 모든 근거 페이지가 상위 5개 검색 결과에 있는지 |
| `answer_generated` | 유답 질문에서 발췌 초안 생성. 의미상 정답 확정은 아님 |
| `missed_answer` | 유답 질문인데 관련 근거 없음으로 처리됨 |
| `correct_abstention` | 무답 질문을 관련 근거 없음으로 처리함 |
| `false_answer` | 무답 질문에 원문을 선택함 |
| `execution_error` | 시간 초과·모델/검색 오류 등. 무답 성공으로 세지 않음 |

근거 포함률 계산에서는 검색 순위와 무관하게 원문의 읽기 순서를 사용하고 중복 Block을
제거한다. 표 행·열의 의미 대응이나 OCR 문자 오류율을 측정하는 지표는 아니다.
페이지를 찾았더라도 답이 있는 행을 가져오지 못할 수 있다. 정상 생성된 초안도 누락·관계
오해·불필요 인용은 별도 검토해야 한다.

현재 정답에는 초안 분류와 전체 페이지 읽기 순서/영역 정답이 없으므로 해당 정확도는
미측정이다. 실행 시간에는 검색·모델 로딩·추론·작업 회수가 포함된다. 120초는 모델 대기
제한이며, 전체 문항 소요 시간이 이를 약간 넘을 수 있다.

## 실제 문서 예비 평가 결과 — 2026-10-12~13

사용자가 제공한 PDF 8개, 605페이지와 질문 40개(유답 32, 무답 8)를 대상으로
실제 PaddleOCR → Layout → E5/Chroma → Qwen3-4B 발췌 파이프라인을 평가했다.
합성 시험과 분리된 첫 실제 문서 기준선이다. 현재 결과는 운영 품질 합격으로 판단하지 않는다.

40/40문항 실행 완료. 유답 32개와 무답 8개의 결과는 다음과 같다.

| 대상 | 결과 | 문항 수 |
|---|---|---:|
| 유답 | 발췌 초안 생성(정확성 별도 검토) | 15 |
| 유답 | 관련 근거 없음으로 처리 | 12 |
| 유답 | 모델 시간 초과 | 5 |
| 무답 | 관련 근거 없음으로 정상 거절 | 7 |
| 무답 | 무관한 원문을 선택 | 1 |

정답 49개 인용문의 공백 제외 완전 일치 포함 수는 OCR 37개 → 상위 5개 검색 21개 →
모델 후보 12개 → 최종 선택 2개다. 이는 정답률이 아니며 아래의 원문 오타·표·대체 근거
한계를 함께 읽어야 한다. 정답의 모든 근거 페이지를 검색한 유답 문항은 26/32개다.

### 결과와 재현 자료

- [문항별 HTML 보고서](../data/real-evaluation-20261012/report.html)
- [지표·실행 결과 표](../data/real-evaluation-20261012/summary.md)
- [전체 집계 JSON](../data/real-evaluation-20261012/summary.json)
- [생성된 초안 내용 검토 목록](../data/real-evaluation-20261012/review-queue.md)
- [실행·재개 방법과 지표 정의](#실제-문서-예비-평가-실행)

PDF 해시·페이지 수가 정답 목록과 일치한다. 원본 자료와 질문은 수정하지 않았고,
평가 결과·DB·페이지 이미지는 Git 제외 경로에 보관했다. 앱의 기본 DB와 검토 기록은
변경하지 않았다. 다운로드 없이 기존 로컬 모델을 사용했다.

### 확인된 결함과 다음 수정 순서

1. **문장·문단 단위의 근거 묶음과 표의 행·열 관계 보존**
   - DOC05-Q01은 4단계 가운데 첫 두 단계가 있는 OCR 한 줄만 선택했다.
   - DOC06-Q02는 다섯 번째 단계의 뒷부분을, DOC06-Q04는 줄바꿈 이후 핵심 조치를 누락했다.
   - DOC08-Q03도 세 유형 가운데 앞줄을 빠뜨렸다.
   - 모델 입력은 Chunk를 개별 OCR Block으로 풀고 각 Block을 독립 검증한다.
     따라서 검색 성공 뒤에도 문장이 분리된다. 다음 구현은 연결된 문장/문단을 선택·검증하는
     단위로 만들되, 원래 Block ID·좌표·원문과 과거 구조 버전은 그대로 보존한다.
   - 표는 한 페이지 전체를 합치지 않고 머리글·행 이름·값이 같은 근거 묶음에 들어가게 한다.
     서로 다른 단·행의 값이 붙지 않는지 DOC02와 DOC07의 표 문항으로 회귀 검증한다.

2. **질문의 조건을 실제로 충족하는지 검증**
   - DOC07-Q05는 문서에 없는 특정 병원의 2026년 실제 방문 인원 질문이다.
     모델이 PDF 30쪽의 맥락 없는 숫자 `13`을 선택해 무답 처리에 실패했다.
   - DOC03-Q01은 목적을 물었으나 일부 복구 절차를, DOC05-Q02는 분석 활동 대신 단계 목록을
     선택했다. DOC08-Q04도 세척 시험 방법 대신 일반적인 상태조사 문장을 선택했다.
   - 관련 주제를 언급하는 것과 질문의 대상·시점·수량·행위를 뒷받침하는 것을 구분해야 한다.
     숫자 Block을 일괄 차단하면 정상 표 답변도 사라지므로 행·열 문맥과 함께 검증한다.

3. **검색 누락과 모델 입력 제한 분리 개선**
   - DOC03-Q03은 정답 페이지 자체를 상위 5개에서 찾지 못했다.
   - DOC01-Q04는 정답 페이지를 찾았지만 필요한 인용문 일부가 검색 Chunk에 없었다.
   - 검색 결과에 있던 인용문이 후보 제한 뒤 빠지는 경우도 있다. `retrieved_quote_exact`와
     `candidate_quote_exact`를 별도로 기록했으므로 재검색·문단 확장·후보 예산 변경을 비교할 수 있다.
   - 기본 페이지 구조도 별도로 저장했다. 개선안은 새 구조 버전으로 평가하고 기존 기준선을 유지한다.

4. **숫자 교정과 출처 보존**
   - DOC06-Q03의 선택 원문에는 `1,000RLU`와 OCR 오류인 `1,00RLU`가 함께 들어갔다.
     원문 PDF 8쪽 이미지를 대조해 숫자 누락을 확인했다.
   - 숫자·단위 교정을 새 revision으로 저장하고 원문을 보존하는 편집 기능이 필요하다.
     모델이 값을 추정하여 자동으로 고치는 방식은 채택하지 않는다.

5. **실제 입력 크기의 시간 초과 회귀**
   - DOC01-Q01~Q04와 DOC04-Q01은 120초 모델 제한으로 실패했다.
     실행 오류를 무답 성공으로 세지 않았다.
   - 실행 중 다른 앱의 GPU 메모리 사용도 확인했으나, 단독 원인으로 단정하지 않았다.
     긴 입력의 생성·독립 검증 시간과 GPU 메모리 조건을 분리해 재시험해야 한다.
     이번에는 사용자 앱 종료나 모델 시간 제한 확대를 하지 않았다.

### 정답과 평가 지표의 한계

- 질문 파일의 `needs_human_review` 상태를 유지했다. 정답 초안의 의미 정확성을 사람이
  최종 승인한 평가가 아니다. 생성 성공 횟수는 정답률이 아니다.
- DOC03-Q01의 인용문은 `destroyed`지만 PDF 2쪽에는 `destoryed`라는 원래 오타가 있다.
  OCR도 원래 철자를 읽었다. 이 사례를 OCR 오류로 해석하면 안 된다. 원문 인용문과
  의미상 정답을 분리해 교정할 필요가 있으며 이번 기준선에서는 원래 정답 파일을 유지했다.
- 공백만 제거한 완전 일치 지표이므로 문장부호·대시·단위 문자 차이도 불일치다.
  표의 행·열 관계와 여러 줄을 건너뛰는 인용문도 단순 문자열 지표의 한계가 있다.
- DOC06-Q03처럼 같은 사실이 다른 페이지에 반복되면 지정 정답 페이지 밖의 유효한 근거가
  엄격한 페이지 일치 지표에서 제외될 수 있다. 대체 근거 목록은 별도 사람 검토가 필요하다.
- 분류 정답과 페이지 전체 읽기 순서·영역 정답이 없어 분류 정확도와 Layout 정확도는
  측정하지 않았다. 영어 자료도 현재 한국어 OCR 구성으로 처리했다.
- 일부 근거 페이지를 이미지로 대조했지만, 605페이지 전체를 사람이 검토 완료한 것은 아니다.

## 배치 분석 정답 평가

저장된 OCR과 사람이 작성한 정답을 비교하는 도구다. 앱 DB를 읽기 전용으로 열고,
원문 이미지·텍스트·좌표·처리 버전을 새 폴더에 내보낸다. OCR/검색 모델 재실행이나
기존 자료 변경 없이 사용할 수 있다. 외부 서비스로 자료를 보내지 않는다.

### 실제 문서 준비

먼저 앱에서 PDF의 OCR을 완료한 뒤, 화면 URL의 `document` 값이나 문서 API에서
문서 ID를 확인한다. 아래 `DOC-ID`를 해당 ID로 바꾼다.

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_layout.py export --database data/handover.db --document-id DOC-ID --source-kind real_document --output data/layout-gold-document1
```

합성 문서를 내보낼 때는 `--source-kind synthetic`을 사용한다. 도구가 실제 문서 여부를
자동 판정하지 않으므로 자료 성격에 맞게 지정해야 한다. 출력 폴더는 매번 새 이름을 쓴다.

- `dataset.json`: OCR 원문 스냅샷과 정답 입력란.
- `reference.html`: 페이지 원문 이미지, OCR 문장, Block ID와 좌표를 함께 보는 자료.
- `page-00001.png` 등: 정답 작성에 필요한 해당 버전의 원문 이미지 사본.

내보낸 자료에는 문서 원문이 포함된다. Git에서 제외된 `data` 안에서 관리한다.
내보내기는 DB 스냅샷을 읽으며 앱의 원문·색인·검토 기록을 수정하지 않는다.

### 수동 정답 작성

`reference.html`을 브라우저에서 열고 원문과 대조하면서 `dataset.json`의 각 페이지에서
아래 필드만 편집한다. `page`, `source_sha256`, 문서·ingestion ID는 수정하지 않는다.
읽기 순서를 모델 예측으로 채우지 않는다. 화면의 **검토 완료** 기록도 자동으로 정답으로
간주하지 않는다. 정확한 순서·분류 정답을 별도로 작성해야 한다.

```json
{
  "annotation_status": "reviewed",
  "expected_order": ["BLOCK-A", "BLOCK-C", "BLOCK-B"],
  "expected_kinds": {"BLOCK-A": "heading", "BLOCK-B": "paragraph"},
  "note": "두 단은 왼쪽 열 전체를 먼저 읽음"
}
```

위 예시는 페이지 안의 정답 필드만 나타낸 것이다. 내보낸 원문 필드는 유지한다.
Block ID는 실제 자료의 값을 사용한다.

- `annotation_status=draft`: 미작성/검토 중. 정답 필드가 있어도 점수에서 제외한다.
- `annotation_status=reviewed`: 사람이 작성한 정답을 평가에 포함한다.
- `expected_order=null`: 읽기 순서 미작성. 분류 정답만으로도 평가 가능하다.
- `expected_order=[]`: 글자가 없는 페이지의 명시적 정답.
- 읽기 순서를 작성하면 공백 행을 제외한 모든 Block을 정확히 한 번 포함해야 한다.
- `expected_kinds`: 일부 Block만 작성 가능. 제목 `heading`, 본문 `paragraph`,
  표 후보 `table_candidate`, 판별 보류 `unknown` 중 하나다.
- 표 후보 평가는 Block이 표 영역에 속하는지에 대한 분류이며 셀/병합/행열 복원 평가는 아니다.

### 평가 실행

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_layout.py score --input data/layout-gold-document1/dataset.json --output data/layout-score-document1
```

`evaluation.html`은 표 형태의 결과와 페이지별 차이를 표시하고, `evaluation.json`은
자동 비교에 사용할 수 있는 전체 수치를 저장한다. JSON에는 자료/분석기 버전,
입력 파일 SHA-256, 문서·OCR ID, 정답 작성률, 오류 Block ID를 기록한다.

원문 해시가 달라진 자료, 다른 OCR 버전 혼합, 중복 페이지, 잘못된 Block ID,
읽기 순서의 누락·중복은 평가를 거절한다. 분석기가 원문 Block을 누락·중복하거나
원문 범위와 다른 좌표를 반환해도 평가 전체가 실패한다.

### 지표 해석

| 지표 | 계산 범위 |
|---|---|
| 분류 정답 작성률 | 검토 완료 페이지의 분류 정답 Block / 자료 전체의 공백 제외 Block |
| 분류 일치율 | 분류 정답이 있는 Block 중 예측과 정답이 같은 비율 |
| 분류별 정밀도·재현율·F1 | 분류 정답이 있는 Block만 대상으로 산출 |
| 페이지 순서 완전 일치율 | 순서 정답이 있는 비어 있지 않은 페이지 중 전체 순서가 같은 비율 |
| 선후 관계 일치율 | 순서 정답 내 모든 두 Block 쌍 중 상대 순서가 같은 비율 |

분모가 없으면 `null`/평가 대상 없음이다. 빈 페이지가 순서 점수를 높이지 않으며,
Block 1개 페이지는 완전 일치에는 포함되지만 선후 비교 쌍은 0개다.
선후 관계는 페이지별 백분율 평균이 아니라 전체 비교 쌍으로 가중 집계한다.
OCR 문자 정확도·OCR 인식 누락·제목 트리·표 셀 복원·검색 관련성은 이 도구의 평가 대상이 아니다.

### 합성 자료 회귀 결과

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_layout.py fixtures --output data/layout-gold-fixtures-new
.\.venv\Scripts\python.exe scripts/evaluate_layout.py score --input data/layout-gold-fixtures-new/dataset.json --output data/layout-score-fixtures-new
```

기존 사람이 작성한 `tests/fixtures/layout_cases.json` 정답을 그대로 변환한다.
2026-10-05 실행 결과: 6페이지(빈 페이지 1개), 29 Block 중 분류 정답 14개(48.28%),
지정된 14개 분류 일치, 비어 있지 않은 5페이지 순서 완전 일치, 86개 선후 관계 일치.
이 자료는 규칙 개발에 사용한 회귀 fixture이므로 실제 업무 문서 일반화 성능을 뜻하지 않는다.
실제 문서 결과는 별도 `real_document` 자료로 기록해야 하며 아직 평가하지 않았다.

전체 테스트 97개 통과/선택 OCR 1개 건너뜀. DB 읽기 전용·정답 검증·의도적 오류의
점수 하락·미작성 제외·HTML 안전 출력과 실제 Edge의 데스크톱/모바일 보고서 표시를 확인했다.

## 가상 기록관리 업무 데이터 (records-v1)

`docs/develop.md` 4.1과 5.3.1의 실험용 정답 데이터다. 가상 기관의 기록관리팀에서
인계자 1명이 업무 25개를 인수자 3명에게 넘기는 상황을 만든다. 문제 생성, 답안 채점,
업무 적합도·준비도 계산의 기준값으로 사용한다.

**검토 상태: 초안.** 사용자가 아래 검토 목록을 확인하기 전에는 정답으로 확정하지 않는다.

### 구성

| 항목 | 수량 | 내용 |
|---|---:|---|
| 업무(Task) | 25 | 중요도·실패 영향·의존성·빈도·긴급성(0~100), 월 평균 소요 시간, 기준 경험 기간, 필요 역량(1~5), 절차·주의사항·문제 해결 |
| 인수자 | 3 | 신규 기록연구사(분류·평가 강함), 보존처리 주무관(보존·재난 강함), 시스템 주무관(시스템·정보공개 강함) |
| 인계자 | 1 | 전보 예정 기록연구사 |
| 인수인계서 | 4 | HO-A 분류·보존기간, HO-B 보존환경·소독, HO-C 복원처리, HO-D 재난 대응 |
| 역량 | 6 | 분류, 평가, 보존처리, 재난 대응, 시스템, 정보공개 |

업무 25개 중 18개는 `data/evaluation-input/`의 실제 매뉴얼 문장을 근거로 작성했고,
`manual_references`에 문서명·PDF 페이지·인용문을 남겼다. 인용문은 40문항 정답 초안에서
확인된 문장만 사용했다. 나머지 7개와 각 업무의 일부 절차는 가상 기관의 내부 기준이며
문장 끝에 `(기관 내부 기준)`을 붙여 구분한다.

인수자 3명은 강점이 서로 다르게 설계했다. 같은 업무라도 인수자마다 적합도와 추천 결과가
달라져야 계산 로직을 검증할 수 있다.

### 파일

```text
datasets/records-v1/dataset.json      정답 데이터(Git 추적)
data/synthetic/records-v1/            생성 결과(Git 제외, 다시 만들 수 있음)
├─ clean/HO-A.pdf … HO-D.pdf          텍스트 PDF
├─ scans/good|medium|poor/HO-*.pdf    텍스트 층이 없는 스캔 PDF
└─ manifest.json                      업무별 PDF 페이지, 스캔 설정, 파일 해시
```

형식과 참조 규칙은 `src/handover_ai/domain/workforce.py`가 검증한다. ID 중복, 정의되지 않은
역량, 없는 업무를 가리키는 수행 이력, 인계자가 아닌 직원의 인수인계서, 범위를 벗어난
역량 수준은 오류로 처리한다.

### 생성

```powershell
.\.venv\Scripts\python.exe scripts\build_synthetic_dataset.py
```

| 품질 | 해상도 | 변형 |
|---|---:|---|
| good | 300 DPI | 변형 없음 |
| medium | 200 DPI | 0.8° 회전, 대비 감소, JPEG 품질 55 |
| poor | 150 DPI | -2° 회전, 흐림, 잡음, 대비 감소, JPEG 품질 40 |

한 업무는 인수인계서의 한 페이지에서 시작하고, 표지에는 업무 현황 표가 있다.
스캔본은 정상본을 페이지 단위로 옮기므로 `manifest.json`의 업무별 페이지가 모든 품질에서 같다.
글꼴은 PyMuPDF 내장 한국어 글꼴을 사용하고, 잡음 난수와 PDF 메타데이터를 고정해
같은 입력이면 같은 파일이 나온다.

PDF에는 실제 인수인계서처럼 중요도를 `높음/보통/낮음` 등급으로만 적는다.
0~100 원점수는 `dataset.json`에만 있으므로, 문서에서 점수를 추출하는 시험은 등급 단위로 비교한다.

### 사용자 검토 목록

- [ ] 업무 25개의 절차가 실제 기록관 업무로 자연스러운가
- [ ] `(기관 내부 기준)` 문장이 실제 규정과 충돌하지 않는가
- [ ] 업무별 중요도·실패 영향·긴급성 점수의 상대적 순서가 납득되는가
      (예: 재난 대응 업무가 보존용품 관리보다 높음)
- [ ] 인수자 3명의 역량·경험·가용 시간이 서로 구분되는가
- [ ] 생성된 PDF 표지와 업무 페이지 몇 장을 열어 보고 형식이 인수인계서로 보이는가

검토가 끝나면 `dataset.json`의 `review_status`를 바꾼다. 내용을 고치면 PDF를 다시 생성한다.
